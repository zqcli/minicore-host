# MiniCore Host 性能优化报告

## 结论与范围

本轮完成静态分析、三个 Astra/max 配置的子代理并行实现、独立交叉 review、
完整本地质量检查，以及基线和优化版本的实际测量。版本保持 **0.9.20**。
基线为 `4ee5e819798c2b165f9b03cf69dcdfb4a82e2cb4`，接受完整测试和测量的
代码检查点为 `dccb62beb676f38e089f1523410d294a3b8d4d82`。
这里的模型设置是派发配置记录，不是独立的运行时模型证明。

最主要的已测收益来自消除 compaction 对不断增长的请求前缀的重复构造和序列化。
在 1,024 组历史、每组 1 KiB 正文的确定性探针中，prepare + generate 耗时的
轮次中位数从 **6,159.14 ms 降至 19.39 ms**，四轮配对耗时比的中位数降低
**99.67%**。这是本地压缩准备与确定性摘要流程的结果，不包含真实模型推理延迟。

Provider 请求编码、大对象协议序列化、大 JSON 严格解码和末页 edit 查询也有
可重复观察到的收益。diff 与部分中小对象序列化结果存在波动和退化；本报告保留
全部 61 个场景，不将局部结果外推为整个 Host、真实模型服务或生产吞吐的统一增幅。

本次公开经过 review 的优化代码、测试、探针、测量 runner、审计脚本、全部
61 项汇总结果和 [仅含清单与校验和的证据 manifest](evidence-manifest.json)。
原始证据包在自动审批拒绝公开上传后单独保留，等待所有者明确授权；第六节说明
发布范围和取得完整证据包后才能执行的复算步骤。

## 一、静态分析与实际改动

完整的实施前分析及排除项保存在 [TASK.md](TASK.md)。八项改动如下。

| 项目 | 静态发现 | 已实施改动 | 保留的行为边界 |
| --- | --- | --- | --- |
| P1：compaction 分块 | 每增加一个候选 exchange，都重建并序列化完整前缀；相近大小的条目使块内准备工作呈平方增长 | 从原构造器产生空请求基数，逐条累计精确 JSON 编码字节；最终请求仍由原构造器产生 | 两层转义、整体取整、previous summary、超大首组、错误候选先验证再判断边界、实际分块和最终请求 |
| P2：协议 DTO | `validated_dto!` 为序列化而克隆字段；部分校验为读取而克隆对象 | 私有 wire 结构借用字段；共享借用式校验 | 原反序列化路径、字段严格性、省略/null、校验顺序和 serializer 名称 |
| P3：diff 分页 | 先为完整 diff 分配行字符串，再截取请求页；片段构造又复制原行 | 借用差异行，仅为返回页分配片段 | 仍计算完整 fingerprint 和 Patience diff；保留 hunk 坐标、游标、UTF-8 边界及取消检查 |
| P4：严格 JSON | 拷贝根及嵌套 RawValue；解码时克隆整棵 Value 树 | 借用 RawValue，从保留的 Value 引用反序列化 | 完整字段解析、重复字段拒绝、精确数字和全量 round-trip 保真检查；原生拥有型数据仍需分配 |
| P5：冷历史分页 | 把完整已验证 journal 投影为公共 DTO 后才取页 | 完整验证后统计公共条目，只投影所请求页 | 完整文件校验、访问/撤销规则、装载协调、公共游标与较新 retained history 的优先级 |
| P6：RPC 响应 | typed result 先变为 Value，再编码完整 RPC envelope | 直接把 typed result 编码到完整响应缓冲 | 完整编码成功才入发送队列；失败返回关联的 `-32603`，无半截结果；原路由和订阅规则 |
| P7：模型请求 | 每次请求先构造拥有型 messages/schema JSON 树，再整体编码 | 私有借用式 request/message/tool 投影；仅在 assistant 文本确需拼接时转为拥有型字符串 | replay、reasoning、工具能力校验；原 ID、可选字段、精确工具参数和实际 HTTP JSON 含义 |
| P8：edit 游标查询 | 后页重复遍历已经由游标排除的前缀 | 在应用 Turn 过滤前跳过已验证前缀 | 绝对索引、过滤语义、next cursor 与边界检查 |

没有增加持久索引、缓存、配额、截断、重试或恢复机制。保持
Host → Agent → Session → Runtime 的直接所有权、accepted-work 生命周期、
current/saved 区别、访问检查、短状态锁，以及保存确认和 fsync 顺序。
没有修改 SPEC、Runtime 锁定版本、依赖、Cargo manifests、历史性能脚本或历史证据。

### 表示与诊断的明确变化

直接编码后，RPC/HTTP 的 JSON 对象成员顺序可能随 typed 字段声明顺序改变；
契约保持解码后的字段和值以及数组、事件顺序。原生 f64 的等价指数写法也可能变化。
不能把这些请求/响应描述为逐字节不变。精确解析的大整数、长小数和工具参数已覆盖
回归测试。compaction 的最终请求构造器未变，其边界及请求一致性有专门回归覆盖。

普通业务 RPC 成功响应路径的 diagnostic 仍在编码完成之后、入发送队列之前结束。
其 elapsed 现在包含最终响应编码；此前在构造中间 Value 后结束。因此这项
diagnostic 的耗时口径有扩大，不能直接把新旧数字当作相同计时区间。
初始化、订阅建立分支保持原计时边界；错误响应 envelope 仍在 diagnostic 结束后编码。

## 二、测量方法

两版使用 Rust 1.90.0、相同锁文件和默认 release profile，构建 jobs=2，
incremental=false。四份 Rust 探针源码对两版完全相同，运行前校验二进制 SHA-256。
环境为 Linux x86_64、AMD EPYC 7763，进程可用 9 个逻辑 CPU。
测量期间没有本项目编译；没有声称机器隔离、CPU 绑核或清空系统缓存。

正式配对测量包含 **4 轮、30 组命令、240 次进程运行、61 个展开场景**。
两轮基线先运行，两轮优化版先运行，并反转场景顺序。全部命令成功。
先核对编码字节、压缩覆盖条目/调用数/token、分页尺寸等语义维度，再计算比值。
探针自身同时检查构造结果与读回数据；归档校验器核对维度、顺序、计数和哈希。

每个进程内的重复样本先取中位数，再按同一轮的 candidate / baseline 配对；
表中百分比为四个配对比值的中位数减一。两列耗时分别是四轮进程结果的中位数，
所以百分比不一定等于直接用这两列相除。所有样本保留，不丢弃离群值。
9 次、101 次进程内重复不是额外独立轮次；协议和 provider 的每次操作耗时由整体
计时除以迭代数得到，不能据此计算单次调用延迟分位数。
32 个协议场景共享同一个协议探针进程，61 项场景也不是 61 个独立统计试验。

必要的生产校验保留在计时内。fixture 构造和事后正确性检查在计时外；只有探针
明确执行的预热被排除，compaction 的三次重复全部保留。IO 的 diff 准备阶段包含
完整查询，不能用其进程峰值推断单页分配量。metadata 为暖文件读取，journal 为
内存后端，不代表冷设备或持久写入/fsync 吞吐。

Compaction 的 64/256/1,024 组场景分别覆盖 62/247/987 条历史，两版均为一次
utility 调用，压缩前后的 token 数完全相同。因此结果不是通过减少被处理历史或
改变分块目标得到的。摘要模型为立即返回的确定性 fixture；大幅下降主要体现
重复前缀处理的消除，不表示外部模型推理加快了同样倍数。

Provider 最大场景生成 **29,360,792 B** 请求。进程在事后 JSON 校验前观测到的
HWM 中位数从 **82,158 KiB 降至 49,396 KiB**，配对中位数降低 **39.90%**。
它包含 immutable fixture、预热及编码过程，只是这个独立进程的峰值观测，
不是分配字节统计，也不是完整 Host 的内存下降百分比。

61 项主耗时指标中，53 项配对耗时比的中位数小于 1、8 项大于 1；33 项在四轮中都降低。
这些计数不具有场景权重或统计显著性含义。不得按场景简单平均后宣称总体提速。
P5 冷历史投影和 P6 直接 RPC 编码的独立收益没有单独的大载荷探针，
报告仅确认静态工作量减少、回归测试通过和 Host 场景兼容性。

### 波动与退化

8 项配对中位数升高的场景全部保留在附表。其中 AgentConfig 的 4 KiB/0 工具、
64 KiB/0 工具、64 KiB/8 工具分别为 +1.08%、+5.88%、+7.26%；
SessionConfig 的 64 KiB/8 工具为 +2.75%。四项 long-diff 的升幅为
+1.45%、+12.93%、+5.47%、+4.86%，均有轮次改善也有轮次退化。
这次四轮测量不能证明它们存在稳定的因果退化，也不足以宣称这些场景已提速。
diff 仍要计算完整 hash 和 diff，本次主要减少返回页之外的字符串构造，
因此耗时变化小且易受调度影响；未测得的分配量不列作量化收益。

## 四、真实 Host 场景复核

使用未修改的 Task090 harness，对每版各启动三个新的实际 Host 进程，运行
Runtime、HTTP/SSE loopback provider、stdio RPC、持久/内存 Session 和真实 bash 工具。
六轮均通过，逐轮为 14 个实际模型请求、104 个模型发出块，每个流式 Turn 的最终
正文为 2,048 B；暂停时 32 个输入没有触发模型请求。每轮取消后均验证 bash 及其
子进程不存在、拥有的进程组消失，关闭诊断也完整。没有 fixture 错误或 WARN/ERROR。

| 观测，单位 ms | 基线中位数 | 优化版中位数 | 基线 p95 | 优化版 p95 |
| --- | ---: | ---: | ---: | ---: |
| 暂停时消息接受 | 0.344 | 0.302 | 1.277 | 0.607 |
| 正文传递，1 Turn / 1 observer | 0.330 | 0.356 | 0.776 | 0.822 |
| 正文传递，4 Turns / 1 observer | 0.514 | 0.374 | 1.687 | 1.187 |
| 正文传递，4 Turns / 2 observers | 0.553 | 0.621 | 4.443 | 2.985 |

正文计时从 fixture 即将写入 HTTP/SSE 到 Python 客户端读完对应 stdout 通知，
包含 loopback、Host、stdio 和客户端调度，不是纯 Host CPU 时间。
较小样本的 p95 只是最大值，多个块和 observer 不是独立进程试验。

两组实际 Host 测量相隔约 22 分钟，基线一分钟系统负载约 1.63–1.78，
优化版约 0.047–0.056；它们不是正式探针那样的交替配对。
模型场景主动等待约 50 ms，并在八个块间间隔 10 ms；取消场景还有约 50 ms 的
真实 FIFO 工具阻塞。这些人工等待影响总耗时和首输出延迟。
基线第二轮还多了 22 次状态收敛轮询；主要业务和模型请求数一致。

完整 Host 的绝对峰值 RSS 中位数从 16,588 降至 16,180 KiB，但空 Host RSS
也从 12,452 降至 11,852 KiB；按每轮计算的 peak-minus-empty 中位数反而由
4,136 增至 4,372 KiB，不能据此宣称工作负载分配减少。
CPU 采样粒度为 10 ms，零增量不等于没有 CPU 工作。
优化版一轮最后的退出态 `Z` 样本没有 RSS，之前的业务采样完整。
详细独立审查单独保存在原始包的 `evidence/validation/host-review.json`，
该文件的校验和列在 [证据清单](evidence-manifest.json)。

这些结果支持本次改动在所测真实功能路径上的兼容性。它们没有证明整体 Host
提速，也不能确立上述亚毫秒波动的因果归属；不覆盖真实外部 provider、WAN、
WSS/TUI 验收、饱和吞吐、容量上限或冷历史大页的独立性能。

验证记录见 [validation.json](validation.json)，本地与 GitHub 提交/tree 的映射
