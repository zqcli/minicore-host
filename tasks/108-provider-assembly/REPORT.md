# Provider 与 Runtime 优化结果

日期：2026-11-13。Host 版本保持 0.10.1，SPEC 4.10.1 补充实现约定。

## 完成的修改

普通有效 SSE 消息直接解码为具体结构，省掉整份通用 JSON 中间对象。
明确的上游错误继续单独识别，首次消息、错误分类与安全重试边界保持。
整帧 UTF-8 校验覆盖未知扩展字段；扩展值按 JSON 库跳过规则处理，实际消费字段仍严格检查。

工具参数只由 Runtime 累计和解析。参数片段直接转交已有字符串，首片直接接管；
通过 JSON 和标准 ToolCall 校验后释放原始缓冲，失败则保留原文。
Provider 只保留协议信息及无法交接的原始片段。工具参数不再经过普通文本字符清理。

Provider 先交出已经收到的结束原因和用量，再交出各工具结束事实。
一个工具验证通过、后一个失败时，失败结果保留两者实际内容，但不执行任何工具。
这些部分结果保存、重读后也不会成为完整模型历史。

## CI 中修正的测试问题

Windows 的关闭测试把“创建已受理”误当成“磁盘保存已经提交”。若强制关闭先运行，
创建可以合法终止，Host 直接停止；这不代表 Host 丢弃了正在进行的保存。

测试现复用已有同步机制，确认真实保存已排队后才发出关闭请求。
保存被阻塞时，仍严格要求 Host 保持停止中、创建尚未结束、数据根仍被锁定；
释放后要求保存完成、初始消息没有执行、最终停止且没有关闭错误。
移除了固定次数的让出线程，没有使用固定睡眠、重试或生产代码钩子。

本地关闭测试 14 项通过；原失败用例以 100 个独立进程复核，全部通过。
生产代码、依赖和工作流均与实测版本一致，因此这项测试同步修复不改变性能结果。
后续原生平台结果以修复后 dev 提交的 [CI](https://github.com/zqcli/minicore-host/actions?query=branch%3Adev)
及交付的验证记录为准。

## 怎样测量

基线与候选使用同一台 Linux 机器、Rust 1.90.0、同一份 release 探针及完全相同的数据。
探针调用实际 Provider SSE 解码和 Runtime ModelDriver，仅用内存字节流代替 HTTP 上游。
没有执行真实工具，也没有调用付费模型服务。

共六组成对测试，交替执行基线/候选、候选/基线，同时交替场景顺序。
正式测量时没有本地编译任务。共 48 个独立进程、6,360 次计时调用和 48 次预热。
每次调用都核对完整请求、回答、工具编号、顺序、全部参数、用量、结束信息和文字片段。
48 个进程均成功，全部结果等价校验通过；所有正式样本均保留。

表中耗时先对每个进程内部的固定次数调用取平均，再分别取每侧六个进程结果的中位数。
百分比根据表中双方中位数计算；不将同一进程内的重复当作独立机器样本。
每个进程的一次预热不计入耗时，原始预热数据仍保留。

## 处理耗时

| 场景 | 数据规模 | 修改前 | 修改后 | 变化 |
| --- | --- | ---: | ---: | ---: |
| 普通文字 | 16,384 个片段，每片 16 字节 | 35.292 ms | 26.999 ms | −23.5% |
| 小工具调用 | 4 个工具，每个载荷 128 字节 | 0.140745 ms | 0.087037 ms | −38.2% |
| 交错大参数 | 16 个工具，每个载荷 1 MiB | 135.760 ms | 78.100 ms | −42.5% |
| 交错多工具 | 128 个工具，每个载荷 4 KiB | 15.106 ms | 10.645 ms | −29.5% |

四种场景的全部 24 个成对进程平均耗时均下降。
六对降幅的中位数分别为 21.8%、38.3%、42.5%、29.5%；这一统计与“双方中位数之比”不同，不能混用。

单次调用仍有抖动：候选文字场景的单次最大值为 60.475 ms，高于基线的 53.812 ms；
小工具基线也出现过 4.203 ms 的单次尖峰。所有这些样本都保留，没有删除或挑选。
本次能够支持平均处理成本下降，不能据此承诺每一次都更快或尾延迟改善。

## 进程峰值内存

| 场景 | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| 普通文字 | 4,906 KiB | 4,948 KiB | +42 KiB，+0.9% |
| 小工具调用 | 2,150 KiB | 2,194 KiB | +44 KiB，+2.0% |
| 交错大参数 | 101.96 MiB | 64.30 MiB | −36.9% |
| 交错多工具 | 6.63 MiB | 5.19 MiB | −21.7% |

大参数和多工具场景的六对峰值内存均下降。普通文字、小工具场景略有增加；
不将这些反向结果省略，也不声称所有场景的内存都下降。

这里记录的是 Linux 整个进程的 VmHWM，包含输入夹具、预期响应、运行时、预热和分配器保留。
它不是参数组装单次操作的独立峰值，也不是内存分配次数。
已分别记录构造后、预热后和计时后的 RSS/HWM；大参数和多工具的构造期峰值低于调用后的峰值，
没有掩盖表中的差异。小场景在构造阶段候选进程已经略高，不能把几十 KiB 的差异直接归因于组装逻辑。

## 代码规模与结论范围

按生产 Rust 与测试代码分开统计物理行数，包含注释和空行：

- 生产 Rust：新增 101 行、删除 55 行，净增 46 行。
- 回归测试 Rust：新增 533 行、删除 54 行，净增 479 行，含关闭测试同步修复。
- 手动测量程序、说明文档不计入以上两项；内嵌测试模块计入测试。

本次没有减少生产代码行数。新增的显式错误分支和边界说明抵消了重复处理代码的删除。
实测收益来自去掉中间 JSON 对象、重复参数缓冲和重复解析，以及及时释放已经完成的原始参数。

以上性能结果只描述本地流消息解码和响应组装，不含 HTTP 等待、模型推理、真实工具执行、
完整 Host Turn 或 TUI。它们不等于整轮对话获得同样百分比的提速。
机器没有独占隔离，也没有宣称清空所有缓存；数据是当前固定场景的结果，不作普遍性能保证。
